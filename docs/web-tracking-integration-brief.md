# Web tracking integration brief

Brief for building a public web tracking page (`tracking.html`) that matches the Patwadi mobile app’s customer tracking experience.

---

## 1. How the app tracks parcels today

### Entry points (authenticated)

| Surface | Mechanism |
|---------|-----------|
| `CustomerHome` | Tap active order → `TrackingDetails` with `{ orderId: uuid }` |
| `MyPackagesScreen` | List tap → `PackageDetails`; “Track a Package” field → `resolveOrderLookup(code\|uuid)` → `TrackingDetails` |
| `PackageDetailsScreen` | “Track” button → `TrackingDetails` |
| `ConfirmOrderScreen` | After Razorpay verify → `TrackingDetails` for new `parcelId` |
| `NotificationsScreen` | Deep link with `orderId` |

There is **no unauthenticated deep link** in the app today. All reads go through Supabase with the customer JWT; RLS restricts `orders` and `custody_events` to the logged-in customer (or operators/admins).

### `TrackingDetailsScreen` data flow

1. Load `orders` row by UUID (`getOrderById`).
2. Load `custody_events` for that parcel (`fetchCustodyEvents`), ordered by `created_at ASC`.
3. Derive state with `deriveParcelState({ events, blockedException })` → `SimplifiedParcelState`.
4. Map to customer labels/dates via `deriveCustomerParcelStatus`.
5. Derive scenery city with `deriveTrackingCityName({ parcelState, pickupLocation, dropoffLocation, corridorKey })`.
6. Render `TrackingWindow` (visual tracker + 5-stage timeline) unless `blocked_exception`.

**Do not use** `orders.status` — it is legacy and not updated by custody flow.

## 2. Public tracking code

**Status: APPLIED / LIVE** — `supabase/schema/phase26_tracking_code.sql` is deployed on project `wvxyaqqlqwbbpkgvrali`. Confirmed orders have `tracking_code` values (new orders via trigger; existing confirmed orders backfilled).

### Format

```
P + YY + DD + MM + NNN + OO
```

| Segment | Meaning | Example (`P262006001DC`) |
|---------|---------|--------------------------|
| `P` | Fixed prefix | `P` |
| `YY` | Year (IST) | `26` → 2026 |
| `DD` | Day of month (IST) | `20` |
| `MM` | Month (IST) | `06` → June |
| `NNN` | Daily sequence (001–999, resets each IST calendar day) | `001` |
| `OO` | Origin + destination city initials from `corridor_key` slug | `DC` = **D**elhi + **C**handigarh |

- `corridor_key` is lowercase underscore-separated, e.g. `delhi_chandigarh` (see `buildCorridorKey()` in `src/lib/domain/corridors.ts`).
- Initials = first character of origin slug + first character of destination slug, uppercased.
- Generated by trigger `trg_set_order_tracking_code` when `payment_status = 'confirmed'` and `tracking_code IS NULL` — fires `BEFORE INSERT OR UPDATE OF payment_status, corridor_key`.
- Column: `orders.tracking_code TEXT`; unique via partial index `idx_orders_tracking_code` (`WHERE tracking_code IS NOT NULL`).
- Daily sequence (`NNN`) stored in `tracking_code_daily_seq` (IST calendar day).

### Recommended web URL

```
https://<your-domain>/tracking.html?code=P262006001DC
```

Optional second factor (future): `?code=...&phone=...` — not implemented in app yet; phone is not stored on `orders` (only on `profiles` via auth).

### In-app lookup

`resolveOrderLookup()` accepts tracking code **or** UUID. Codes exist on every order where `payment_status = 'confirmed'`. RLS still applies — logged-in customer only sees their own orders.

**Web lookup:** use the **`public-track-parcel`** edge function (§8) — no anon RLS on `orders`.

## 4. Schema columns for tracking

### `orders` (primary)

| Column | Type | Tracking use |
|--------|------|--------------|
| `id` | UUID | Internal key; app route param |
| `tracking_code` | TEXT (unique when set) | Public lookup key; populated when `payment_status = 'confirmed'` |
| `customer_id` | UUID | RLS owner |
| `pickup_location` | TEXT | Route display; city extraction |
| `dropoff_location` | TEXT | Route display; city extraction |
| `corridor_key` | TEXT | Corridor label; tracking code initials |
| `payment_status` | TEXT | Must be `confirmed` for active parcel |
| `blocked_exception` | BOOLEAN | Forces `blocked_exception` state |
| `trip_id` | UUID → `linehaul_trips` | Operator/internal; not shown Tier-1 |
| `created_at` | TIMESTAMPTZ | “Booked” date |
| `updated_at` | TIMESTAMPTZ | Row touch time (not custody truth) |

Not used for customer status: `status`, `driver_id`, operator IDs (`lmp_pickup_id`, etc.) — Tier-1 derives only from custody.

### `custody_events` (status truth)

| Column | Type | Tracking use |
|--------|------|--------------|
| `parcel_id` | UUID | FK → `orders.id` |
| `from_role` / `to_role` | TEXT | `customer`, `lmp`, `linehaul` |
| `proof_type` | TEXT | `photo` for POD at delivery |
| `proof_value` | TEXT | Storage path for POD photo |
| `created_at` | TIMESTAMPTZ | Stage dates |

Custody transition → state mapping (`deriveParcelState`):

| Event (`from` → `to`) | `SimplifiedParcelState` |
|-----------------------|-------------------------|
| (none) | `created` |
| `customer` → `lmp` | `pickup_confirmed` |
| `lmp` → `linehaul` | `in_transit` |
| `linehaul` → `lmp` | `out_for_delivery` |
| `lmp`/`linehaul` → `customer` | `delivered` |
| `blocked_exception = true` | `blocked_exception` (overrides all) |

### `linehaul_trips` (internal)

Used for operator trip windows and corridor timing — **not** exposed Tier-1. Linked via `orders.trip_id`. Web page should not show trip/conductor details.

### `corridors`

| Column | Use |
|--------|-----|
| `key` | Matches `orders.corridor_key` |
| `origin_city`, `destination_city` | Human-readable corridor |

## 5. Customer-facing stages: **5 (authoritative)**

**Source of truth:** `PATWADI_LAUNCH_ARCHITECTURE.md` §9, implemented in:

- `src/components/CustomerParcelTrackerCard.tsx`

| # | `SimplifiedParcelState` | Customer label |
|---|-------------------------|----------------|
| 1 | `created` | Booked |
| 2 | `pickup_confirmed` | Picked up |
| 3 | `in_transit` | In transit |
| 4 | `out_for_delivery` | Out for delivery |
| 5 | `delivered` | Delivered |
| — | `blocked_exception` | Delivery exception — our team is resolving it |

### 6-stage demo (not authoritative)

`docs/patwadi-tracking-window-india-v2.html` previously had six timeline labels (`On corridor`, `Reached city` as separate steps). That was an **early visual prototype**. Production app and `TrackingWindow.tsx` use **5 stages**. The HTML demo has been aligned to 5.

**Note:** Time-of-day chips in the window scenery (`On corridor`, `Reached city`, `Out for delivery`) come from `TIMES[].statusText` in `trackingScenery.ts` — they decorate the sky scene by clock time, **not** extra timeline stages.

## 6. City derivation (`deriveTrackingCityName`)

Port this logic for web scenery parity:

| `parcelState` | City shown |
|---------------|------------|
| `created`, `pickup_confirmed` | Pickup city (parsed from `pickup_location`) |
| `in_transit` | Pickup city, else corridor origin from `corridor_key`, else dropoff |
| `out_for_delivery`, `delivered`, `blocked_exception` | Dropoff city |

City parsing: match against known `LOCATIONS` list in `trackingScenery.ts`, or first segment of address, or corridor slug → display name via `CITY_SLUG_TO_NAME`.

## 7. `resolveSceneForCity` (web parity)

From `src/lib/domain/trackingScenery.ts`:

```typescript
resolveSceneForCity(cityName) → { displayCity, location, resolved }
```

Algorithm:

1. `findLocationEntry(cityName)` — exact city match, alias, partial match, or fallback `{ city: cityName }`.
2. `resolveScene(location)`:
   - If `aliasOf` → use aliased city’s `CITY_SCENES`.
   - Else if city in `CITY_SCENES` → city-specific skyline SVG.
   - Else → `STATE_SCENES[state]` generic skyline.
3. Returns `resolved.scene.renderSkyline(W, H)`, `motif`, and `displayCity`.

Web implementation options:

- Port `trackingScenery.ts` + `trackingSkylineRenderers` to the static page (same as RN).
- Or reuse generated preview assets in `docs/tracking-window-preview.html`.

Time-of-day: `getTimeOfDay()` → `morning` \| `afternoon` \| `evening` \| `night` (local browser time is acceptable for web).

Copy strings: `getTrackingCopy(timeOfDay, displayCity)` for headline/subtitle.

## 8. RLS and public read strategy

Current policies:

- **`orders` SELECT:** `auth.uid() = customer_id` (plus operator/admin policies).
- **`custody_events` SELECT:** participant users or parcel owner customer.
- **No anon read by `tracking_code`.**

**Status: IMPLEMENTED** — `public-track-parcel` edge function. Anon clients call it with a tracking code; the function uses the service role server-side and returns Tier-1 sanitized JSON only. No anon RLS policy on `orders`.

### Recommended approach for public web

**Option A (preferred): Edge Function `public-track-parcel`** *(IMPLEMENTED)*

| Item | Value |
|------|-------|
| Endpoint | `https://wvxyaqqlqwbbpkgvrali.supabase.co/functions/v1/public-track-parcel` |
| Auth | None (public). Deploy with `verify_jwt = false`. |
| Methods | `POST` (preferred) or `GET ?code=` |
| Rate limit | 30 requests / hour / IP via `rate_limit_log` |
| CORS | `https://patwadi.com`, `https://www.patwadi.com` (override with env `CORS_ALLOWED_ORIGIN`) |

#### Request (POST)

```http
POST /functions/v1/public-track-parcel HTTP/1.1
Host: wvxyaqqlqwbbpkgvrali.supabase.co
Content-Type: application/json

{ "tracking_code": "P262006001DC" }
```

#### Request (GET)

```
GET /functions/v1/public-track-parcel?code=P262006001DC
```

#### Response 200 (sanitized)

```json
{
  "tracking_code": "P262006001DC",
  "corridor_key": "delhi_chandigarh",
  "origin_city": "Delhi",
  "destination_city": "Chandigarh",
  "state": "in_transit",
  "label": "In transit",
  "stage_index": 2,
  "stage_dates": {
    "created": "2026-06-20T04:12:00.000Z",
    "pickup_confirmed": "2026-06-20T06:30:00.000Z",
    "in_transit": "2026-06-20T09:15:00.000Z"
  },
  "last_updated_at": "2026-06-20T09:15:00.000Z",
  "tracking_city": "Delhi",
  "scene": {
    "display_city": "Delhi",
    "motif": "India Gate arch · red sandstone domes"
  },
  "blocked_exception": false,
  "blocked_message": null,
  "pod_url": null
}
```

Omitted from response: `customer_id`, operator IDs, Razorpay IDs, `trip_id`, full pickup/dropoff addresses, phone, email, pricing.

At `delivered`, `pod_url` is a short-lived signed URL to the custody POD photo (1 h TTL) when available.

#### Errors

| Status | Body | When |
|--------|------|------|
| 400 | `{ "error": "Missing tracking_code" }` | No code in body/query |
| 404 | `{ "error": "Tracking code not found" }` | Invalid format, unknown code, or unpaid order (same message — no existence leak) |
| 429 | `{ "error": "Rate limit exceeded", "retryAfterSec": 3600 }` | IP over limit |

#### curl

```bash
curl -sS -X POST \
  "https://wvxyaqqlqwbbpkgvrali.supabase.co/functions/v1/public-track-parcel" \
  -H "Content-Type: application/json" \
  -d '{"tracking_code":"P262006001DC"}'
```

#### Website integration (`tracking.html` on patwadi.com)

1. Parse `?code=` from the URL (or read from an input field).
2. `fetch` the edge function — **no** Supabase anon key or service role in the page:

```javascript
const code = new URLSearchParams(location.search).get("code");
const res = await fetch(
  "https://wvxyaqqlqwbbpkgvrali.supabase.co/functions/v1/public-track-parcel",
  {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ tracking_code: code }),
  }
);
const data = await res.json();
if (!res.ok) throw new Error(data.error || "Lookup failed");
// Render timeline from data.state, data.label, data.stage_index, data.stage_dates
// Render scenery from data.tracking_city, data.scene.display_city, data.scene.motif
```

3. CORS: browser requests from `https://patwadi.com` are allowed. Set Supabase function secret `CORS_ALLOWED_ORIGIN=https://patwadi.com,https://www.patwadi.com` if you need a custom list.

4. Deploy / update function:

```bash
cd E:/PatwadiApp/patwadi
supabase functions deploy public-track-parcel --no-verify-jwt
```

Implementation: `supabase/functions/public-track-parcel/index.ts`, shared derivation in `supabase/functions/_shared/publicTracking.ts`.

**Option B: RLS policy for anon** *(not built — do not use)*

```sql
-- Example only — NOT deployed; Option A is preferred
CREATE POLICY "Anon read order by tracking_code"
  ON orders FOR SELECT TO anon
  USING (tracking_code IS NOT NULL AND current_setting('request.headers', true)::json->>'x-tracking-code' = tracking_code);
```

Supabase anon clients cannot pass custom headers easily; Option A is simpler and safer.

**Do not** expose service role key in the web page.

## 9. Web page implementation checklist

1. Parse `?code=` from URL.
2. Call edge function (or authenticated Supabase if user is logged in on web).
3. Run same derivation as app (`deriveParcelState`, `deriveCustomerParcelStatus`, `deriveTrackingCityName`) — copy TS modules or precompute server-side.
4. Render 5-stage timeline matching `CUSTOMER_STATUS_LABELS`.
5. Render window scenery via `resolveSceneForCity` + time-of-day.
6. Show route card (pickup/dropoff/corridor).
7. At `delivered`, show POD if edge function returns signed URL.
8. WhatsApp support link optional (mirror `SupportSheet` context with stage label + tracking code).

## 10. Order creation (when `tracking_code` is assigned)

Orders are created **only after payment verification** — not at booking draft:

| Path | Function |
|------|----------|
| Production | `supabase/functions/verify-razorpay-payment` → `INSERT orders` with `payment_status: confirmed` |
| Dev QA | `skip-dev-payment` (when `ALLOW_DEV_PAYMENT_SKIP=true`) |

DB trigger `trg_set_order_tracking_code` sets `tracking_code` on insert when `payment_status = 'confirmed'`. Existing confirmed orders backfilled by `phase26_tracking_code.sql`.
